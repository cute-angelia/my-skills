# v-novel-镜灵章节审查

这是一个章节正文审查 + 实改流水线。

核心不是写报告，而是反复把章节改到能读、能追、更像番茄爽文正文。每一轮审查后，只要发现问题，就必须进入修改；不要只把问题留给用户。

## 触发场景

当用户说以下类似需求时触发：

- “用 v-novel-镜灵章节审查看这章”
- “镜灵章节审查一下”
- “按镜灵流程把这章改到能发”
- “这章用毒舌读者、番茄组、反 AI 多轮审”
- “目标 9.7 分以上，没到继续改”

## 防串项目规则

默认只处理用户本轮给出的文本、文件，或用户当前明确指定的项目材料。

除非用户本轮明确要求沿用某个旧项目、旧角色、旧世界观，否则：

- 不把历史记忆里的项目名、角色名、设定名写进正文
- 不把其他作品的风格契约当成当前章节规则
- 不把其他项目的审查结论套到当前文本
- 所有判断必须来自当前章节、当前项目文件或用户本轮明确要求

## 输入优先级

1. 用户本轮最新要求
2. 目标章节正文 / 目标文件
3. 当前项目明确给出的创作规范、风格契约、设定集、前后章节
4. 本 skill 的镜灵审查流程
5. 关联 skill 的规则：`v-novel-anti-ai`、`v-novel-multi-role-review`、`v-novel-write-shuangwen`

如果资料不全，可以继续改，但必须标注“本轮只基于已给文本判断”。不要假装看过不存在的设定或前文。

## 固定执行步骤

### Step 1：先用 v-novel-anti-ai

先进入 `v-novel-anti-ai` 的口径：

- 找 AI 味、总结腔、报告腔、解释腔、概念空转
- 找硬设计味、账本化、风控化、政务法规化
- 找不服务剧情的停顿、动作、环境、精致物件、氛围句
- 找台词过完整、像旁白转述、像作者替人物说明的问题

默认直接实改，不只输出诊断。

### Step 2：毒舌读者第一轮

让“毒舌读者”严格看一遍。

毒舌读者第一轮必须额外检查“锚点缺失”。

毒舌读者只回答四件事：

1. 哪里最假、最水、最像 AI
2. 哪里最想弃文
3. 哪些地方看似有停顿、有画面，但其实不推进剧情、不制造压力、不增加人物信息
4. 是否存在锚点缺失：读者不知道这一段的人、事、地点、目标、冲突、利害、时间承接、情绪来源、动作对象分别是什么

锚点缺失检查口径：

- 人物锚点：这一段是谁在看、谁在说、谁在做，是否清楚
- 场景锚点：人在哪里，周围有什么会影响行动或压迫感
- 目标锚点：主角此刻要拿什么、躲什么、逼谁表态
- 冲突锚点：当前对抗点是什么，谁和谁的利益撞上了
- 利害锚点：这句话/这个动作造成什么损失、收益、风险或站队变化
- 时间锚点：这一段和上一段的承接是否断裂，是否像突然跳镜头
- 情绪锚点：人物为什么怒、怕、忍、酸、急，是否只剩抽象情绪词
- 动作对象锚点：动作落在谁/什么物件/什么证据上，是否悬空

凡是毒舌读者指出的问题，必须修改。锚点缺失不能只补旁白说明，优先用人物动作、台词打断、现场物件、利益变化、对方反应补锚。

### Step 3：番茄爽文金番作家实改正文

让“番茄小说爽文金番作家”下场改正文。

固定写法要求：

- 用番茄爽文写法
- 开篇与关键段落追求黄金 3s 抓力
- 增强各方视角，但不要机械切镜头
- 去 AI 味，去解释腔，去总结腔
- 增强网文张力，增强追读压力
- 表达生活化，不要端着写
- 对话不要写成旁白
- 台词不要太完整，允许打断、省略、反问、半句话、话里有刺
- 写正文，不写分析稿
- 让剧情从利益碰撞里长出来
- 注意不从作者视角硬推

利益碰撞硬要求：

- 每一场戏至少要有一个利益变化：钱、权、脸面、资格、证据、资源、靠山、选择权、话语权、群体立场
- 每个人都要有自己的算盘：主角要拿回什么，反派怕失去什么，配角为什么站队，旁观者为什么动摇
- 不能靠作者宣布“局势变了”，必须让人物通过选择、误判、下注、威胁、翻脸、倒戈来推动

删除规则：

- 如果某段看起来有停顿、有画面，但不推进剧情、不制造压力、不增加人物信息，删
- 如果某个动作只是精致、只是氛围、只是“像小说”，删
- 如果某段只是把信息摆整齐，像账本，删或打散进现场
- 如果某段像风控报告、政务法规、规则讲解、合规说明，改成现场动作和人物试探
- 如果桥段有硬设计味，改成角色利益自然顶出来

### Step 4：毒舌读者第二轮

毒舌读者再严格看一遍。

重点查：

- Step 3 有没有把正文修得太顺、太满、太像作者安排
- 爽点是否真落地，还是只在旁白里说爽
- 反派是否降智
- 配角是否只会震惊
- 台词是否还像解释设定
- 有没有新的 AI 味、账本味、风控味、政务法规味

发现问题就继续修改正文。

### Step 5：用 v-novel-multi-role-review 番茄组审查并修改

调用 `v-novel-multi-role-review` 的“番茄组”：

- 番茄爽文作家
- 番茄爽文短篇读者 / 番茄爽文读者
- 金番作家

审查重点：

- 爽点是否够直给
- 黄金 3s 是否成立
- 章节是否有继续往下刷的冲动
- 情绪是否有压迫、反击、回报
- 人物是否有商业识别度
- 场景是否有利益变化
- 章末是否有钩子

番茄组指出的问题必须修改，不得只留建议。

### Step 6：毒舌读者第三轮

毒舌读者再严格看一遍。

这一轮只盯“读者会不会骂”的点：

- 水
- 假
- 装
- 尬
- 端
- 解释太多
- 爽点没兑现
- 看起来热闹但没推进
- 作者痕迹太重

有问题就继续改。

### Step 7：圆桌会议冲 9.7 分

组织四方圆桌：

1. 番茄小说爽文金番作家
2. 番茄小说爽文短篇读者
3. 毒舌读者
4. 组内总编 / 会议主持

目标：让实稿评分超过 9.7 分。

圆桌流程：

1. 四方各自给当前稿评分，满分 10 分
2. 每方只说最影响分数的 1-3 个硬问题
3. 主持人合并成“必须改”的短清单
4. 根据会议结论直接修改正文
5. 再次评分
6. 如果未达到 9.7，继续重复“指出硬问题 → 修改正文 → 再评分”

迭代上限：

- 原则目标是达到 9.7 分以上
- 为避免无限循环，单次执行最多进行 3 轮完整圆桌迭代
- 如果 3 轮后仍未到 9.7，必须输出：当前分数、卡分原因、下一轮最该改的 3 个点，并交付当前最好版本

评分标准：

- 9.7+：可作为当前终稿交付
- 9.3-9.6：能读，但仍有明显追读 / 爽点 / AI 味短板，继续改
- 9.0-9.2：结构或正文有硬伤，必须大改
- 9.0 以下：不交终稿，先重构冲突与利益链

### Step 8：最后再用 v-novel-anti-ai

终稿前再跑一遍 `v-novel-anti-ai`。

重点清理：

- AI 味
- 总结腔
- 报告腔
- 解释腔
- 账本化
- 风控化
- 政务法规化
- 硬设计味
- 过完整台词
- 不服务剧情的停顿、画面、动作、环境

最后交付修改后的正文。

## 输出格式

默认输出：

```markdown
# 镜灵章节审查终稿

## 终稿正文
（直接给可替换正文）

## 极简修改说明
- 本轮主要改了：...
- 最终评分：.../10
- 若未到 9.7：卡分原因：...
```

如果用户明确要求“保留审查过程”，再输出每一轮的简短审查记录；否则不要把大量中间报告塞给用户。

## 最终自检

交付前逐项检查：

- [ ] 是否先走过 `v-novel-anti-ai`
- [ ] 是否经过至少一轮毒舌读者
- [ ] 第一轮毒舌读者是否检查了锚点缺失，并用动作、台词、现场物件、利益变化或对方反应补锚
- [ ] 是否让番茄爽文金番作家实改正文
- [ ] 是否使用番茄组审查并修改
- [ ] 是否进行圆桌评分，目标 9.7+
- [ ] 是否最后再跑一遍反 AI
- [ ] 是否删除了不推进剧情、不制造压力、不增加人物信息的画面停顿
- [ ] 是否去掉硬设计味、账本化、风控化、政务法规化
- [ ] 是否让剧情从利益碰撞里长出来，而不是作者硬推
- [ ] 是否交付正文，而不是只交付分析
