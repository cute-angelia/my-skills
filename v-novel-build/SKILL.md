# v-novel-build

这个 skill 只解决一件事：
当用户要在 `novelOs` 体系里“开始用一个小说项目”时，先帮他在 3 个项目里选对，再按那个项目的正确入口继续推进。

固定项目根目录：
`/Users/vanilla/git/github/cute-angelia/novelOs`

固定三选一：
- `open-novel-writing`
- `novel-pro`
- `webnovel-writer`

统一反 AI 审查规则：
- 这三个项目只要涉及“AI 味审查 / 去模板化 / 去解释腔 / 正文反 AI 诊断 / 审查报告”，统一优先使用 `v-novel-anti-ai`
- 不再为三个项目分别维护多套 AI 审查口径
- 各项目自己的 workflow / checker / review 流程可以继续存在，但凡是“文风 AI 味审查”这一层，统一以 `v-novel-anti-ai` 为主口径

不要把三者混成一个系统。
它们不是不同名字的同一套东西，而是三个层级不同的方案。

## 防串项目规则

本 skill 只负责选择和启动当前小说项目，不把历史记忆里的某本书默认写进新项目。

除非用户在当前任务里明确说要沿用某个旧项目、旧角色、旧设定或旧世界观，否则：
- 初始化文件不得出现历史项目的角色名、设定名、地名、组织名
- 不把其他项目的审查结论写成当前项目事实
- 不把长期记忆当成当前项目素材来源
- 当前项目事实只来自项目目录内文件、用户本轮指令、当前会话明确确认的信息


## 何时触发

当用户出现以下意图时触发本 skill：

- “帮我开始写一本小说”
- “这三个小说项目该用哪个”
- “用 novelOs 搭一个写作项目”
- “接管我已有的小说”
- “继续写下一章”
- “我忘了 open-novel-writing、novel-pro、webnovel-writer 的区别”
- “在这三个项目里选一个给我用”
- “帮我开一个长期写作系统”
- “帮我做轻量写作原型”

如果用户已经明确说了项目名，直接进入对应分支，不要重复让他选择。
如果用户只说“写小说 / 搭项目 / 接管旧稿”，但没有指明项目，必须先分流。

## 三个项目的一句话定位

### 1. open-novel-writing

一句话：
轻量写作规则包 / 原型系统。

适合：
- 快速试验写作规则
- 做轻量版创作助手
- 提炼去 AI 味规则
- 低门槛原型验证

不适合：
- 当成成熟的长期主系统
- 指望它提供完整状态管理和工程闭环

### 2. novel-pro

一句话：
长篇小说工作流框架 / 真相系统。

适合：
- 新书启动流程设计
- 旧稿接管
- 逐章结算
- 真相总账 / 快照视图 / 同步门禁
- 长篇治理

不适合：
- 期待现成 CLI 工程产品级体验
- 把它当最完整的自动化生产系统

### 3. webnovel-writer

一句话：
工程化主系统 / 真正可长期使用的连载系统。

适合：
- 日常持续写作
- 长篇连载
- 设定 / 大纲 / 章节 / 审查闭环
- 数据回写
- 恢复与持续生产

不适合：
- 只想随手试个轻量原型
- 不愿处理更高复杂度的工程环境

## 默认选择规则

当用户没有明确指定时，先按意图判断，再给出选择：

1. 如果用户要“长期稳定写长篇、持续连载、要工程闭环”，优先推荐 `webnovel-writer`
2. 如果用户要“治理工作流、接管旧稿、逐章补账、做真相系统”，优先推荐 `novel-pro`
3. 如果用户要“快速试规则、做轻量原型、先跑概念验证”，优先推荐 `open-novel-writing`

但即使你有明显推荐，也不要替用户直接拍板。
在用户未指定时，先给用户一个三选一入口，让用户确认要用哪一个。

## 未指定项目时的标准提问模板

当用户没有指定项目时，先用尽量短的方式让他选：

```text
你这里有 3 个小说项目，我先帮你分一下工：
1. open-novel-writing：轻量规则包 / 原型，适合快速试写作规则
2. novel-pro：长篇工作流框架，适合接管旧稿、逐章结算、真相系统
3. webnovel-writer：工程化主系统，适合长期稳定连载

你这次要用哪一个？
如果你告诉我目标，我也可以直接帮你推荐一个。
```

如果用户目标已经很明显，也可以这样问：

```text
按你这个需求，我更建议你用 webnovel-writer（长期主系统）。
如果你要，我也可以改走：
1. open-novel-writing
2. novel-pro
3. webnovel-writer
你选一个，我就按那个继续。
```

## 分流后怎么做

## A. 选择 open-novel-writing 时

目标理解：
这是“轻量规则包 + 演示级自动化脚本”，适合低门槛推进，不要假装它有完整工程状态系统。

默认做法：
1. 读取 `open-novel-writing/SKILL.md`
2. 确认用户当前要做的是哪一类：设定 / 大纲 / 章节规划 / 正文 / 评审 / 批量推进
3. 如果要写正文，必须让用户指定风格类型；若未指定，先补这一项
4. 以模块化方式推进，不强绑完整项目目录
5. 明确告诉用户这是轻量原型链，不是长期工程闭环
6. 如果用户要做“AI 味审查 / 去 AI 味 / 去模板化 / 去解释腔 / 反 AI 审查报告”，统一转给 `v-novel-anti-ai` 执行，不单独发明 open-novel-writing 私有审查口径

最低目录参考：
- `设定/`
- `大纲/`
- `规格/`
- `正文/`
- `评审/`

何时推荐改用别的：
- 用户开始要求长期连载、稳定状态管理、恢复和审查闭环时，提示可升级到 `webnovel-writer`
- 用户开始强调逐章接管、总账、快照、同步门禁时，提示可切到 `novel-pro`

## B. 选择 novel-pro 时

目标理解：
这是“workflow + agent + 真相系统”的长篇治理框架，关键是分流、接管、结算、门禁。

先判断用户属于哪种入口：
1. 新小说启动
2. 存量小说接管
3. 继续写下一章
4. 单章审计 / 修订

对应做法：

### B1. 新小说启动
- 先确认用户是否已有创作思路
- 若有，就吸收已有材料，只补缺项
- 若没有，就走启动问答
- 启动问答至少覆盖：题材、世界观基调、主角身份、开局处境、主线冲突、篇幅推进方式、文风读感、禁区
- 先输出启动摘要，再回填初始化文件
- 初始化文件只允许写入“当前项目已明确提供或本轮问答明确确认”的信息
- 严禁把跨项目记忆、别的作品例文名、旧角色名、旧项目设定、历史审查结论直接写进当前项目初始化文件
- 若外部记忆/上下文与当前项目材料冲突，必须一律降权；以当前项目目录内的草稿、设定、卷纲、用户本轮明确说明为准
- 若用户没有明确说“本作最终形态是短剧/短剧小说化/微短剧”，不得擅自把“短剧规格”“短剧风格”“每章≈一集”“例文骨架参照”等内容写入 `创作契约`、`元数据`、`作者意图` 等初始化文件

### B2. 存量小说接管
- 检查目录结构
- 补齐真相文件骨架
- 从 `故事/同步状态.md` 判断当前进度
- 必须逐章读取、逐章结算，不可跳章，不可预读后文

### B3. 继续写下一章
- 先检查 `故事/同步状态.md`
- 若仍有待同步章节，不允许直接续写
- 通过后再执行固定流水线：
  `Planner -> Composer -> Writer -> Observer -> Settler -> Auditor`

### B4. 单章审计 / 修订
- 只处理目标章节
- 不默认推进后续章节
- 需要说明本次是否涉及补结算

执行硬规则：
- 先看 workflow 再进 agent，不要一上来把全部资料塞满
- 先事实总账，后快照视图，再更新同步状态
- 待同步章节未清空时，不要让系统继续写下一章
- 目标是把长篇写稳，不是图快
- 如果用户要做“正文 AI 味审查 / 去模板化 / 去解释腔 / 反 AI 审查报告 / 按反 AI 模板修”，统一调用 `v-novel-anti-ai` 作为文风审查主口径，不再单独维护 novel-pro 私有反 AI 审查规则

## C. 选择 webnovel-writer 时

目标理解：
这是三者里最适合长期实战的主生产系统，优先用真实 CLI / preflight / 项目状态来执行，不只靠静态脑补。

固定源码仓库：
`/Users/vanilla/git/github/cute-angelia/novelOs/webnovel-writer`

本地源码态硬规则：
1. `WEBNOVEL_REPO_ROOT` 固定为上面的路径，不要再搜索旧路径
2. `PROJECT_ROOT` 指向真实小说项目根，不是插件目录，不是源码仓库目录
3. 不要把正文、设定、大纲、状态文件写回插件目录或源码仓库
4. 能跑 CLI 时优先跑真实预检，不要只靠猜

进入任何 `webnovel-*` 流程前，默认先读：
1. `${PROJECT_ROOT}/创作规范.md`
2. `${PROJECT_ROOT}/设定集/风格契约.md`
3. 若 1 不存在，再用 `/Users/vanilla/git/github/cute-angelia/novelOs/创作规范.md` 作为兜底骨架

最常见入口：
- 初始化项目：`/webnovel-init`
- 规划章节：`/webnovel-plan 1`
- 写第 1 章：`/webnovel-write 1`
- 审查范围：`/webnovel-review 1-5`
- 启动面板：`/webnovel-dashboard`

源码态下的最低动作顺序：
1. 确认 `PROJECT_ROOT`
2. 运行 `preflight`
3. 通过后再进入 `plan / write / review / resume / dashboard`

若只知道工作区父目录，不知道项目根：
- 先用 `where` 解析真实项目根
- 再执行 `preflight`

审查链注意：
- 非 Claude Code 或 Task/subagent 不稳定环境，默认把多检查员并行降级为串行
- 四个核心检查员保底顺序：
  1. consistency-checker
  2. continuity-checker
  3. ooc-checker
  4. reader-pull-checker
- 以上检查员继续负责一致性/连续性/OOC/读者拉力等工程审查；但凡涉及“正文 AI 味审查 / 去模板化 / 去解释腔 / 反 AI 审查报告”，统一优先走 `v-novel-anti-ai`，不再单独维护 webnovel-writer 私有反 AI 文风审查口径

何时不建议选它：
- 用户只是想快速试试规则，不想搭工程
- 用户目标只是做最轻量的写作原型

## 输出要求

无论用户最终选哪一个，输出都尽量遵循：

1. 先说明“本次你帮他选了哪个项目 / 或他选了哪个项目”
2. 用 1-3 句说清为什么是它
3. 再进入对应项目的下一步
4. 不要同时给三套大流程，避免信息爆炸

推荐格式：

```text
本次我们用：webnovel-writer
原因：你要的是长期稳定连载，它最适合做主生产系统。
下一步我会先确认 PROJECT_ROOT，然后做 preflight，再进入计划/写作流程。
```

## 禁止事项

1. 不要在用户未指定时，直接假定他一定要 `webnovel-writer`
2. 不要把 `open-novel-writing` 说成成熟主系统
3. 不要把 `novel-pro` 说成现成完整工程产品
4. 不要把 `webnovel-writer` 说成只是 prompt/skill
5. 不要混用三者目录和状态文件
6. 不要在该分流时跳过选择环节
7. 不要给出模糊回答，比如“都可以，看情况”后就结束

## 最短记忆版

记不住时，按这三句执行：

- `open-novel-writing` = 轻量规则包 / 原型
- `novel-pro` = 长篇工作流框架 / 真相系统
- `webnovel-writer` = 工程化主系统 / 长期生产闭环

用户没指定，就先让他三选一；
用户指定了，就直接进入对应项目。
