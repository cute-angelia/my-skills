# 小说反 AI 审查技能

## 适用场景

当用户出现以下意图时，直接触发本 skill：

- “这段有 AI 味，帮我看一下”
- “把这章处理得更像真人写的”
- “去掉总结感/报告感/模板感”
- “按小说反 AI 模板审一下”
- “检查这段正文哪里假、哪里像 AI”
- “保留剧情不动，帮我审下文风和表达”

注意：
- 以上触发词只代表“进入反 AI 审查流程”，不代表自动获得改稿授权
- 只要用户没有明确说“直接改正文/按报告实改/给我成稿”，默认都先交审查报告

本 skill 默认用于“审查已有文本并输出报告”，不是直接改稿，也不是重做剧情大纲。
如果用户同时要求改剧情，先区分：

1. 剧情结构问题
2. 文风 AI 味问题
   优先处理第 2 类，避免一边改剧情一边误伤人物与设定。

默认流程：
1. 先做反 AI 审查报告
2. 由用户决定是否进入实改
3. 未经用户明确授权，不直接覆盖或重写正文

## 默认执行口径

遇到这类请求时，默认按下面顺序理解：

1. 用户提到“有 AI 味 / 帮我处理 / 帮我修一遍 / 更像真人写的”
   - 先视为“要审查，不是要你直接代改”
2. 用户提到“按报告改 / 继续实改 / 直接出成稿”
   - 才进入正文实改
3. 如果用户表达含糊，但又明显不想看长分析
   - 也先给短版审查报告 + 1~2 段示例，不直接整章重写

## 总原则

1. 不改核心剧情，不改人物关系，不改关键设定，不改事实顺序。
2. 优先删除而不是堆砌新句子。
3. 优先把“抽象感受”改成“动作、停顿、物件、视线、话里带刺”。
4. 优先把“解释”改成“呈现”。
5. 优先把“整齐、均匀、全都像写出来的句子”打散。
6. 默认先交付审查报告，不直接交付整段重写正文；只有用户明确要求实改时才进入改写。
7. 禁止修成文案腔、散文腔、金句腔、鸡汤腔。
8. 审查报告要能让用户看出“哪里有问题、为什么有问题、建议怎么改”，而不是空泛点评。
9. 少解释，少总结，少排比；多动作，多压迫，多角色视角里的阴冷判断。

## 核心处理流程

### Step 1：先判定问题类型

拿到正文后，逐段扫描以下高频 AI 症状：

- AI 词汇
- 感悟式结尾
- 抽象心理
- 节奏过平
- 水文与重复描写
- 不服务剧情的环境描写
- “像 XXX/像是/仿佛在说”类比句
- 带解释的破折号句式
- 非破折号式描述
- 装饰性动作
- 物件反复出场制造“精致感”
- 语气描写直接端出来
- 多余收尾句
- 信息整理太工整，像作者在汇报设定
- 解释太满，留白不足
- 逻辑推演太直白，像 AI 在讲规则漏洞
- 反派出场像功能性 NPC
- 台词偏解释型，不够自然
- AI 式收束句（如“他开始想第二步了”）
- 抽象判断词偏多

如果同一段命中 2 条以上，默认把它列为“高优先级问题段”，在报告里给出重写建议或示例改法，而不是直接整段改写。

### Step 2：按反 AI 表逐项处理

以下规则来自“小说-反 AI 模板”，执行时从上到下检查：

| 问题类型                                         | 修订方式                                         |
| ------------------------------------------------ | ------------------------------------------------ |
| AI 词汇                                          | 替换为更自然、更口语化、人物化的表达             |
| 感悟式结尾                                       | 删除，或改成悬念、动作未尽、话没说透的结尾       |
| 抽象心理                                         | 外化成动作、表情、停顿、对话、位置变化           |
| 节奏问题                                         | 调整长短句比例，避免每句都完整圆润               |
| 水文                                             | 删除重复信息、重复情绪、重复动作                 |
| 环境描写                                         | 删除不服务剧情、不推动气氛、不映照关系的环境描写 |
| 像 XXX                                           | 删除不服务剧情的比喻和类比                       |
| “把手机翻过去扣在桌上”                           | 默认删掉，除非它真影响剧情                       |
| “挂了电话。”                                     | 默认删掉，除非后文动作必须承接这一拍             |
| 非服务剧情                                       | 直接删掉                                         |
| 物品类精致描写（如“摸了一下手腕上的玉镯，凉的”） | 一章最多保留 2 次，且必须真有用                  |
| “语气很平”                                       | 删掉，改成台词内容或动作带出                     |
| “都是这种平”                                     | 删掉                                             |
| 破折号后带解释                                   | 删掉解释部分，能直说就直说，能不说就不说         |
| 非破折号式描述                                     | 避免用“X——Y”“X—Y”硬拐解释；优先改成自然句、动作句、直接呈现 |
| “像在说今天天气不错”这类句式                     | 删掉                                             |
| “像是”句式                                       | 大部分删掉，改成直接呈现                         |
| “没有 xxx，没有 xxx，连 xxx”这类句式             | 删掉                                             |
| “不是 xxx，是 xxx”这类句式                       | 删掉                                             |
| “不能 xxx，不能 xxx，更不能 xxx”这类句式         | 删掉                                             |
| 信息整理过于工整                                 | 打散成角色感知、现场动作、局部信息，不要像作者汇报设定 |
| 解释太满                                         | 删掉二次说明，保留让读者自己接住的空白               |
| 逻辑推演太直白                                   | 不把规则漏洞讲穿，改成角色试探、停顿、试错、旁敲侧击 |
| 反派像功能性 NPC                                 | 补反应、补压迫、补欲望与算计，不只让他承担剧情功能   |
| 台词解释味太重                                   | 去掉“说明/定义/复述型”台词，改成人物会真说出口的话   |
| AI 式收束句                                      | 删掉“他开始想第二步了”这类总结尾巴，改成动作未尽或压迫未落地 |
| 典型 AI 判断句                                   | 像“不是小摩擦能有的”这类替读者下判断的句子，默认删掉或改成现场迹象与人物反应 |
| 抽象判断词偏多                                   | 少写“冷、荒唐、危险、复杂、微妙”，多写动作、站位、眼神、停顿 |

### Step 3：四类重点改写手法

#### A. 抽象改具象

把：

- 她有些难受
- 他心里一沉
- 她忽然意识到
- 她感到荒唐

优先改成：

- 手停了一下
- 话到嘴边又咽回去
- 人站着没动，先看了他一眼
- 她把那句原本要说的话换掉了

规则：读者要“看到”反应，不要只“知道”反应。

#### B. 结尾去感悟化

禁用这类收尾：

- 原来……
- 她终于明白……
- 命运从这一刻开始……
- 有些东西早就变了，只是她现在才知道

优先保留这类收尾：

- 一个动作没做完
- 一句对话戛然而止
- 新信息刚落地
- 人物关系突然偏移
- 下一步危险已经逼近

结尾应该把读者往后拽，不要往回总结。

#### C. 去解释腔

发现以下结构时优先压缩：

- 动作 + 解释动作原因
- 台词 + 解释语气/心理
- 比喻 + 解释比喻含义
- 破折号后追加翻译说明

例：

- 差：她笑了一下，笑意却没有到眼底，显得格外冷淡。
- 优：她笑了一下，眼神没动。

#### D. 打散匀称句

AI 常把句子写得过分平均、完整、顺滑。
处理时要主动制造：

- 短句插刀
- 省略
- 卡顿
- 话说半截
- 动作先于判断
- 对话里带信息差

目标不是“故意口水”，而是恢复人的呼吸感。

#### E. 去设定汇报感

以下情况要重点压：

- 一段里连续整齐交代世界规则、人物定位、利害关系
- 信息摆得太平，像作者在给读者做 briefing
- 角色刚出场就把功能、身份、威胁一次性讲完

处理方向：

- 把信息拆回现场，让人物在动作、试探、压迫、反应里带出
- 只保留当前场景必须知道的信息，其余延后
- 优先让读者先感到人、再感到规则，不要先读到说明书

#### F. 去规则讲解腔

重点拦截这类写法：

- 主角把漏洞想得过于完整，像在做题解
- 一段话把“规则 -> 漏洞 -> 利用方式 -> 后果”全讲完
- 明明可以通过博弈展示，却改成脑内讲义
- 直接替读者下判断，比如“不是小摩擦能有的”“不是普通人能干出来的”这类结论句

处理方向：

- 少解释规则，多写试探
- 少总结漏洞，多写角色怎么踩边、怎么试错、怎么收住
- 把“聪明”写成压迫感，不写成说明能力

#### G. 去功能性反派

反派如果一出场只负责：

- 递威胁
- 送情报
- 推剧情
- 被主角识破

就会很像功能性 NPC。

处理方向：

- 补他的判断、欲望、戒备、误判
- 让他像一个在场的人，而不是一个被作者派来完成剧情按钮的人
- 即便台词不多，也要让读者感觉到他在盯、在压、在算，不只是来走流程

## 硬性删改黑名单

以下内容默认高优先级排查：

1. “把手机翻过去扣在桌上”
2. “挂了电话。”
3. “语气很平。”
4. “像在说今天天气不错。”
5. “像是……”
6. 破折号后补解释
7. 非破折号式描述（如“她看着他——不是心软，是在算账”这类硬拐说明）
8. 物件冷/凉/硬/温热之类的精致触感描写反复出现
9. 不推动剧情的环境描写
10. 不推动关系的感慨句
11. 明明能从动作看出来，却再解释一遍心理
12. 信息整理太工整，像作者在汇报设定
13. 解释太满，留白不足
14. 逻辑推演太直白，像在讲规则漏洞
15. 反派像功能性 NPC
16. “他开始想第二步了”这类 AI 式收束句
17. 抽象判断词堆叠
18. “不是小摩擦能有的”这类典型 AI 判断句

如果用户没有特别要求保留，这些内容优先在审查报告里标成“建议直接删”。

## 默认输出：审查报告

除非用户明确说“直接改”“给我成稿”“直接重写”，否则默认只输出审查报告。

标准输出结构：

1. 总体判断
   - 这段/这章的 AI 味主要集中在哪几类问题
   - 严重度（轻 / 中 / 重）

2. 高优先级问题段
   - 逐段指出问题
   - 说明为什么像 AI
   - 给出删改方向

3. 删改原则
   - 本次优先删什么
   - 本次优先保留什么
   - 哪些地方不能误伤剧情/人物/设定

4. 示例改法（可选）
   - 只给 1~3 段示例
   - 作用是示范改法，不是把整篇直接改完

5. 待用户确认
   - 是否按这份报告进入实改

报告要短、准、能执行，不要写成空泛长评。

## 实改触发条件

只有在用户明确表达以下意图时，才允许从“审查”进入“实改”：
- “直接改正文”
- “给我成稿”
- “按这个报告改”
- “继续，直接修正文”
- “不要分析，直接重写”

其中：
- “帮我处理一下”“修一遍”“更像真人写的”这类话，不算实改授权
- 没有明确授权时，只给审查报告或审查报告 + 少量示例改法

## 实改前 Git 保护

一旦用户明确授权进入“正文实改”，默认先做 Git 基线保护，再动正文。

但执行口径要更实用：
1. 能直接做 Git 基线保护的，就直接做，不必反复征求用户
2. 如果判断明确、风险低、路径清楚，直接进入“基线保护 -> 正文实改”
3. 只有在以下情况不确定时，才停下来告诉用户，由用户决定：
   - 不确定项目根目录是不是这一个
   - 不确定是否该在当前目录初始化 Git
   - 不确定是否会把用户未想纳入版本控制的大文件/缓存文件一起提交
   - 不确定当前改动范围是否超出用户本次授权
   - Git 命令失败、仓库状态异常、存在冲突或其他异常风险

标准动作：
1. 先检查目标小说项目根目录是否已经有 `.git/`
2. 如果没有，且项目根目录判断明确：
   - 直接在项目根目录执行 `git init`
   - 写入最小 `.gitignore`
   - 将当前正文、设定、大纲、评审等文件做一次基线提交
3. 如果已经有 Git：
   - 直接 `git add -A`
   - 以“实改前基线”语义提交一次，如：`反AI实改前备份：第12章`
4. Git 基线提交成功后，直接进入正文实改
5. 如果遇到不确定项，不要硬做；明确告诉用户卡点，让用户决定

目的：
- 保证用户随时能回滚到实改前版本
- 保证反 AI 修订不是不可逆改稿
- 方便用户对比“原稿 / 审查建议 / 实改稿”的差异
- 在判断清楚时减少不必要确认，提升执行效率

如果 Git 不可用或提交失败：
- 必须明确告知用户“当前无法做版本保护”
- 若问题很明确且可选修复方案单一，可顺手给出建议
- 若是否继续存在明显取舍，让用户决定是“只停在审查报告”还是“放弃保护继续实改”

## 质量自检清单

交稿前必须自检：

- 有没有先给出审查报告，而不是越权直接整篇改写？
- 如果进入实改，有没有先完成 Git 基线保护？
- 报告有没有保住原剧情、原人物、原信息？
- 有没有把抽象判断指出并转成可执行的修改方向？
- 有没有点出感悟式尾巴？
- 有没有点出无效环境描写？
- 有没有点出“像是 / 像在 / 仿佛 / 似乎”这类句式？
- 有没有点出解释性破折号？
- 有没有点出装饰性小动作？
- 问题优先级是不是清楚？
- 报告是不是更像编辑审查意见，而不是空泛评论？

若答案有 2 项以上是否定，继续重修，不要交。

## 特别提醒

1. 反 AI 不等于堆脏字、堆口语、故意写乱。
2. 反 AI 不等于把每句话都改短。
3. 反 AI 的关键不是“更花”，而是“更准、更省、更像人物自己会这么活着”。
4. 如果原文最大的毛病是“什么都解释”，就要狠删。
5. 如果原文最大的毛病是“空”，就补动作，不补感悟。

## 一句话执行口令

当用户只给一句话命令时，按这个理解执行：

“按小说反 AI 模板修” = 默认理解为“按反 AI 模板审查”，先不动剧情设定与正文成稿，逐段排查 AI 词汇、感悟式结尾、抽象心理、解释腔、无效环境描写和装饰动作，输出可执行的审查报告与少量示例改法，再由用户决定是否进入正文实改。
